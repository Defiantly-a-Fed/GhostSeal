Storage architecture finding:
- ESP32 Ghost Seal hardware currently has no SD card.
- Final architecture must not depend on ESP32 local SD storage.
- Logs, payload assets, captures, command history, and future web/payload assets must live on Node 1 Pi Zero 2 W.
- ESP32 should act as the radio execution board.
- Node 1 should act as controller, logger, storage brain, and recovery supervisor.

Storage rule:
If a Marauder feature requires local SD or local payload files, Ghost Seal must not crash or silently fail.

It must either:
1. request the asset from Node 1 over UART/USB serial, or
2. return a structured JSON error saying Node 1 remote storage is required.

Future storage status event:
{
  "event_type":"ghostseal_storage_status",
  "local_sd":false,
  "remote_storage":true,
  "node1_required":true
}

Future storage request flow:
ESP32 Ghost Seal sends:
{
  "event_type":"ghostseal_storage_request",
  "asset":"evilportal/index.html"
}

Node 1 replies with asset data or a clear error.

Pi Zero 2 W / Ragnar integration decision:
The Pi Zero 2 W becoming the storage brain does NOT interfere with Ragnar if designed correctly.

Correct Node 1 layout:
- Ragnar-derived controller = high-level brain
- ghostseal-bridge service = serial driver / storage bridge / logger / recovery layer
- ESP32 Ghost Seal = radio execution board
- Pi local filesystem = logs, payloads, captures, command history, validation logs

Critical design rule:
Only one service should own the ESP32 serial port.

Bad architecture:
- Ragnar talks directly to /dev/ttyUSB0
- logger talks directly to /dev/ttyUSB0
- dashboard talks directly to /dev/ttyUSB0
- storage bridge talks directly to /dev/ttyUSB0

Good architecture:
- ghostseal-bridge owns /dev/ttyUSB0
- Ragnar talks to ghostseal-bridge
- dashboard talks to ghostseal-bridge
- logger/storage is handled by ghostseal-bridge

Recommended Node 1 architecture:
Ragnar-derived controller
        |
        v
ghostseal-bridge service
        |
        v
USB/UART serial
        |
        v
ESP32 Ghost Seal firmware

Node 1 responsibilities:
- send commands to Ghost Seal
- parse JSON replies
- log all serial output
- store captures/payloads/assets
- expose stable API to Ragnar
- detect ESP32 reboot/crash
- retry or reset if needed
- eventually coordinate dual communication with ESP32-C5 supervisor

ESP32-C5 / dual communication note:
ESP32-C5 can later be used as a supervisor/recovery/secondary communication board.

Possible C5 responsibilities:
- heartbeat monitoring
- crash detection
- reset control for ESP32-S3
- backup command channel
- health/status reporting
- dual serial bridge
- safe-mode recovery

Important:
C5 should not be used to hide broken firmware policy. The direct active-command bypass must still be fixed inside Ghost Seal.
